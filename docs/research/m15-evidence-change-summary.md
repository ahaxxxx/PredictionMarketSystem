# M1 / M5 修改说明与验证结果

日期：2026-11-08。分支：`feat/optimizer-m15-evidence`。

## 本次目标和结果

原先 M5 主要整理评价报告，下一轮 M1 仍按原有数值反馈搜索。本次增加了一条实际接通的反馈路径：**M5 产生证据和结构化建议，下一轮提议器引用这些建议修改候选，再交给现有 M2—M4 评价。**

第一版使用确定性的离线响应验证接口，没有调用真实 LLM。原有随机、进化模式继续可用。

## 当前 M5 和 M1 各自负责什么

M5 先由程序计算可回查的证据：因子的有效修正输入是否非零、预测触及概率边界的比例，以及已有快评 Brier。再按确定性规则给出“保留该维度”“比较其他权重”“向零调整幅度”等待检验建议。

概率因子的有效输入按原组合器处理为“因子概率减市场概率”，避免把没有增量的概率输入当成有效修正。

M1 的新增路径读取建议后，一次修改一个因子权重或全局入场门槛。提议保留父候选、证据编号、参数增减方向与理由。只有引用和参数合法、配置未重复，且预测或拟交易行为有变化，才登记并交给原评价器。

无效响应、调用失败或预算耗尽都有记录，剩余候选名额由 L1/L2 补足，不无限重试。局部冻结的维度仍可能由随机探索覆盖，不会永久删除。

## 已完成的实际运行

以下结果是功能验证，不用于比较收益优劣。

| 运行 | 轮次 / 候选评价数 | 接受的证据驱动提议 | 离线后端调用 | 真实 LLM 调用 |
|---|---|---:|---:|---:|
| 合成开发数据 | 3 轮 / 24 个 | 9 | 2 | 0 |
| 已有 NFL 历史开发数据 | 3 轮 / 24 个 | 11 | 2 | 0 |
| 后端预算设为零 | 3 轮 / 24 个 | 0，L1/L2 完成全部候选 | 0 | 0 |

历史运行来自一场事件的 32 个观测点，不将其当成 32 个独立事件。该运行另外记录了 24 次 M5 特征回放和 24 次提议检查所需的父子特征回放，没有为诊断新增收益评价。

已追踪到的一个具体修改是：第一轮证据显示盘口因子存在非零有效输入；第二轮某个提议将父候选的盘口权重由 0 改为 -0.25，保持另一个因子权重和入场门槛不变。程序确认行为改变后，候选进入原 M2—M4。这证明反馈已经接通，不表示负权重更好。

2. **事件级 M3 开发验证集。** 现有入口仍使用原开发面板切片，等待事件清单和独立输入接口衔接。
3. **双父代重组和更广的策略结构。** 本版只修改已有因子权重与全局 edge，没有搜索任意代码或组合完整策略家族。
4. **独立最终测试和效果对照。** 本轮未证明泛化、收益或 LLM 优势。下一步统一数据协议和评价口径，再比较 EA、数值反馈 LLM 与证据反馈 LLM。

## 队友如何开始核对

先阅读 [实现与运行说明](m15-evidence-loop.md)，再查看 `m5.py` 的 `build_review()`、`llm_proposer.py` 的 `GuidedProposer.propose()`，以及 `run.py` 传递 `review` 的位置。

最小运行命令（仓库根目录，使用新的输出目录）：

```bash
uv sync --frozen
uv run python -m pms.optimizer.run --demo --proposal-mode offline-evidence --output .data/m15-review-demo
```

运行后依次查看：

1. `iterations/001/diagnostics.json`：第一轮证据、诊断和建议。
2. `proposal_calls.json`：下一轮请求是否携带上一轮复盘。
3. `proposal_attempts.json`：提议被接受或拒绝的原因及候选 ID。
4. `iterations/002/proposals.json`、`results.json`：下一轮是否真的生成并评价了这个候选。

建议共同确认：现有提议和复盘格式是否足够衔接；M2/M3 事件清单如何传入；先导实验固定采用哪套评价口径和模型预算。
